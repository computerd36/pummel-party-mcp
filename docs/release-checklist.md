# Release checklist

For the maintainer. Plugin and server are released together, with the same version number. Nothing here is automated: the maintainer does every upload, publish and tag by hand. `scripts\prepare-release.ps1` does everything short of that.

Order of the release: build and verify the packages (section 3), tag the released commit (end of section 3), publish to npm (section 6), upload to Thunderstore and wait for approval (section 4), and only then make the repository public (section 1) and create the GitHub release (section 5). The public steps come last so that the install instructions in the README work from the moment people can read them. Until then the npm and Thunderstore pages link to a repository that is not visible yet. Everything that cannot be undone comes after the tag.

Never reuse a version number. A version uploaded to Thunderstore or npm can never be uploaded again, even if it is deleted. If something is wrong after an upload, fix it and release the next version.

## 0. Before you start

- [ ] Close the game. Run `scripts\verify-backup.ps1` (see the README, "Safety model") and make sure the backup of your real mods is current and verified.
- [ ] If you have not already, decide the version (MAJOR.MINOR.PATCH). Below, `<v>` stands for it.
- [ ] Release gates met: the planned work is closed and reviewed; any outside contact that you wanted to wait for is answered, or you decided to go ahead (record the outcome in your local notes).
- [ ] The planned normal-play behaviour is implemented and the README section "What is active during normal play" no longer contains the TODO paragraph (replace it with the final text). Do not release with that TODO in the README.

## 1. Public repository

- [ ] Final scan before the repository becomes public, of tracked files and of every commit (contents and messages): personal data (names, e-mail addresses other than the commit address, local paths, mod names, Workshop ids, tokens). Useful starting points: `git grep -n -I -i -E "<your name>|<your user folder>|token"`, `git log -p --all -S"<string>"`, and `git log --format=%an%n%ae%n%cn%n%ce | sort -u` for author identities.
- [ ] `git ls-files` shows no `*.dll`, `*.pdb`, `*.exe`, `*.token`, no `decompiled/`, nothing over 5 MB (CI checks this too).
- [ ] `CHANGELOG.md`: change the heading `## [Unreleased] - <v>` to `## [<v>] - <date>`, and read the entry once more for accuracy. Copy the file over `packaging\thunderstore\CHANGELOG.md` (they must be identical; `prepare-release.ps1` checks it, and `package-thunderstore.ps1` packages the root file).
- [ ] `ROADMAP.md` is up to date.
- [ ] Decide whether `CLAUDE.md` stays tracked or becomes local and untracked (`git rm --cached CLAUDE.md`, add it to `.gitignore`), unless something in the repository still depends on it.
- [ ] Issue template (`.github/ISSUE_TEMPLATE/`) is present. Optionally enable GitHub's "private vulnerability reporting" in the repository settings.
- [ ] The repository is made public by the maintainer (GitHub settings). Do this last, together with the GitHub release, when the npm package is published and the Thunderstore package is visible (see the order at the top).

## 2. Version numbers

Set every one of these to `<v>` by hand. `scripts\prepare-release.ps1 -Version <v>` checks the ones it can and reports mismatches; it does not edit files.

| File | What | Checked by prepare-release |
|---|---|---|
| `src/PummelPartyMcp.Plugin/PummelPartyMcp.Plugin.csproj` | `<Version>` (the single source for the DLL version and for the Thunderstore manifest `version_number` and the zip name) | yes |
| `src/PummelPartyMcp.Plugin/PluginInfo.cs` | `PluginInfo.Version` (shown in the log, `ping`, `get_status`; also the BepInEx plugin version) | yes |
| `src/PummelPartyMcp.Server/package.json` | `version` (the server reports it as its MCP server version) | yes |
| `src/PummelPartyMcp.Server/package-lock.json` | top-level `version` and `packages[""].version` (run `npm install --package-lock-only` in the server folder after changing `package.json`, then check both) | yes |
| `CHANGELOG.md` | the heading for this version (and the identical copy `packaging/thunderstore/CHANGELOG.md`) | yes |
| `docs/plugin-api.md` | the title line `(api v2, plugin <v>)` | yes |
| `packaging/thunderstore/README.md` | uses `{{VERSION}}`, filled in by `package-thunderstore.ps1`; no edit | n/a |
| Thunderstore `manifest.json` | generated by `package-thunderstore.ps1` from the csproj version; there is no file to edit | n/a |
| `README.md`, `src/PummelPartyMcp.Server/README.md`, `skills/` | no current version string today. Look for statements such as "Pre-1.0", "unreleased" or "not published" and fix them. The text "(0.8.0)" next to some tools is history, not the current version, and stays | by hand |
| Comments in the code, tests | tests do not assert the version number. Comments such as "plugin 0.8.0" mark when a feature was added and stay | by hand |

Do not change `PluginInfo.ApiVersion` unless the HTTP contract changes in a breaking way; the server and the plugin must agree on it. Also set the tested game versions (`TestedVersions` in `src/PummelPartyMcp.Plugin/Core/GameVersionGate.cs`) and the version named in the READMEs if the game has been updated.

`"private": true` in `src/PummelPartyMcp.Server/package.json`: remove it (and the `"//"` note beside it) only now, in the release commit. The `repository`, `homepage` and `bugs` fields already point at the GitHub repository; check them.

## 3. Build, test and package (local)

The plugin cannot be built in CI, because it needs the game's assemblies. Everything below runs on your PC with the game installed.

- [ ] Commit the version changes. The working tree must be clean.
- [ ] Run `.\scripts\prepare-release.ps1 -Version <v>` (add `-GameDir "<Steam>\steamapps\common\Pummel Party"` unless it is set in `src\GameDir.props.user`). It:
  - checks that the tree is clean and that the version numbers agree;
  - builds the plugin in Release;
  - runs `PummelPartyMcp.Plugin.Tests`, `PummelPartyMcp.Plugin.PatchTests` (the drift test) and the server tests;
  - builds `release-out\PummelPartyMcp-<v>.zip` through `package-thunderstore.ps1` and `release-out\pummel-party-mcp-<v>.tgz` through `npm pack`;
  - prints the SHA-256 of both files.
  Write the two SHA-256 values down.
- [ ] CI is green on the release commit (server tests, plugin core tests, npm package file list, forbidden-files check).
- [ ] In the game, with the freshly built DLL (copy it into the game folder by hand, after checking what you replace; keep the old DLL):
  - the log shows the new plugin version and "publish block complete";
  - `self_test` returns `ok: true`;
  - build, validate, save and AI-playtest a fresh `MCP_` mod; read playtest state, events, a screenshot and the log;
  - try the tools you changed in this release (imports, prefabs, settings);
  - confirm Workshop publishing is blocked while the plugin is enabled;
  - confirm your real mods still match the backup (`scripts\verify-backup.ps1 -CompareSource`).
- [ ] The zip contains exactly: `manifest.json`, `README.md`, `CHANGELOG.md`, `icon.png`, `BepInEx/plugins/PummelPartyMcp/PummelPartyMcp.Plugin.dll`. No other DLL (the packaging script refuses extras).
- [ ] Tag the released commit now that the packages are built and verified: `git tag -a v<v> -m "pummel-party-mcp <v>"`, then `git push origin v<v>` (by hand). The tag must point at the commit the zip and the tarball were built from. Do this once, before anything is uploaded; the uploads in sections 6 and 4 come after it, and the GitHub release (section 5) comes last.

## 4. Plugin distribution (Thunderstore)

Facts: community `pummel-party` (https://thunderstore.io/c/pummel-party/), team computerd36, package name `PummelPartyMcp`, category Tools, not NSFW. The package name can never be changed later.

- [ ] The manifest depends on `BepInEx-BepInExPack-5.4.2305` (BepInEx 5.4.23.5, Mono; looked up on 2026-11-16, set in `scripts\package-thunderstore.ps1`). Before uploading, open the BepInExPack page in the community and check that this version still exists and still matches the BepInEx version the plugin is built and tested against (5.4.23.5).
- [ ] The icon `packaging/thunderstore/icon.png` is your final 256x256 PNG.
- [ ] Manifest check: `name` is `PummelPartyMcp`; `version_number` is `<v>`; `website_url` is the GitHub repository; `description` is at most 250 characters (the script checks).
- [ ] Open the zip and check its list of entries (the script prints it).
- [ ] Validate the zip with Thunderstore's manifest validator (on the upload page) and look at the README in the markdown preview.
- [ ] After the tag (see the order at the top): upload by hand: community Pummel Party, team computerd36, category Tools. A version number can never be uploaded twice, so check the version first.
- [ ] A new package may need moderator approval before it is visible. Wait for it; the page is not public until then.
- [ ] Install it once from Thunderstore with a mod manager on a clean profile and check the log line.

## 5. GitHub release

- [ ] The tag `v<v>` exists (end of section 3), the npm package is published (section 6), the Thunderstore package is visible (section 4) and the repository is public. Create the GitHub release from the tag by hand.
- [ ] Attach the same zip, byte for byte (`release-out\PummelPartyMcp-<v>.zip`), and write its SHA-256 into the release notes.
- [ ] The release notes link to `CHANGELOG.md` and tell manual-install users to copy the zip's `BepInEx` folder into the game folder (see the README, "Quick install").
- [ ] Optionally attach the npm tarball too, with its SHA-256.

## 6. Server distribution (npm)

- [ ] Check again, right before publishing, that the package name `pummel-party-mcp` is still free (`npm view pummel-party-mcp` should say 404 before the first publish).
- [ ] `"private": true` is removed (see section 2). Review `files`, `bin`, `engines`, `repository`, `license` in `package.json`.
- [ ] Log in to npm with your account. Use two-factor authentication (2FA); publishing asks for a one-time code.
- [ ] `npm publish --dry-run` in `src\PummelPartyMcp.Server` and review the exact file list: only `dist/**/*.js`, `README.md`, `LICENSE`, `package.json`.
- [ ] Publish by hand, in `src\PummelPartyMcp.Server`: `npm publish ..\..\release-out\pummel-party-mcp-<v>.tgz`. This uploads exactly the tarball whose SHA-256 you wrote down; a plain `npm publish` builds a new one. A published version can never be reused, and unpublishing is restricted by npm.
- [ ] Verify from a clean folder, with no repository checkout (a fresh empty folder and, ideally, a fresh user profile or a second PC): run `cmd /c npx -y pummel-party-mcp` (native Windows needs `cmd /c` for `npx`) and check that it starts and prints the "ready" line on stderr. Then add it with `claude mcp add pummel-party-mcp -- cmd /c npx -y pummel-party-mcp`, start the game, open the Mod Editor, and ask the agent to call `get_status`: the server must find the game through the Steam library and reach the plugin.

## 7. Release mechanics

- [ ] The server and the plugin versions match. The server and plugin agree on the plugin API version (`ping.apiVersion`, currently 2).
- [ ] CI never publishes (it has no secrets). Keep it that way.
- [ ] Exit test: a fresh Windows account or a second PC installs everything from the public instructions without the .NET SDK, connects Claude Code, and builds and playtests a sandbox minigame. The publish block is complete, and your real mods still match the backup.
- [ ] After the release: open `CHANGELOG.md` and add a new `## [Unreleased]` section on top for the next version.
